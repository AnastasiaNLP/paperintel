  Good: "Exact Match", "Accuracy", "F1", "BLEU", "pass@1", "Success Rate", "nDCG@10".

- source_section = paper section where the result appears when visible, e.g. "Experiments". Use null if not visible.

- value_type = "absolute", "relative", "speedup", "memory", or "latency".
- evidence_anchor = object with page, section, and table_or_figure when known.
- evidence_confidence = numeric confidence from 0.0 to 1.0 that the value is anchored to the cited table/prose.
- higher_is_better = true, false, or null when metric direction is unclear.

## Rules:
- Extract ONLY results for the proposed method or clearly named variants of the proposed method.
- If a table contains multiple models, do not extract baseline rows unless they are needed only to describe baseline_comparison.
- Prefer dataset/benchmark names from table headers, column headers, row labels, captions, and nearby prose.
- For QA/RAG tables, do not put dataset abbreviations in metric. Map dataset columns to dataset and use the stated metric.
  Example: if columns are NQ/TQA/WQ/CT and the table reports EM, output dataset="Natural Questions", metric="Exact Match".
- For systems/agent papers, dataset should be the named benchmark or environment, not a broad category.
  Example: dataset="WebArena", metric="Success Rate", conditions_keywords=["GPT-4", "agent setting"].
- Put model/method variants such as RAG-Sequence, RAG-Token, ReAct, CoT-SC, Reflexion, SWE-agent, Top-1, 5-shot, zero-shot, test/dev split in conditions_keywords.
- Do not put metric names in task or dataset.
- Do not put dataset names only in conditions_keywords; dataset must be filled explicitly.
- Do not use broad categories as task when a specific benchmark/dataset/environment name is available.
- Do not invent benchmark values.
- Do not infer values from prose unless the number is explicitly stated.
- If you are unsure whether a number belongs to the proposed method, skip it.
- Use page context only to disambiguate task names, metric names, conditions, or whether a row belongs to the proposed method.
- "value" must be a float. If the value is a percentage, store it as a percentage float, e.g. 85.2 not 0.852.
- "baseline_comparison" may be null. Only compute a simple difference when the proposed method and baseline value are clearly in the same table.
- If no benchmark results can be extracted, return [] and nothing else. Do not explain why.
